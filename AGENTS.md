# AGENTS.md

## Назначение

Этот файл содержит постоянные правила работы Codex с репозиторием.

Не превращай `AGENTS.md` в полное описание проекта.

Подробные продуктовые требования должны храниться в `docs/GAME_SPEC.md`.

Дополнительные документы создавай только тогда, когда они действительно помогают разработке. Не создавай документацию ради документации.

Перед существенной работой изучи относящиеся к задаче документы проекта.

Если какого-либо документа ещё нет, не придумывай его содержимое.

---

## Роли

Пользователь определяет:

* какую игру он хочет получить;
* какой опыт должен получить игрок;
* функциональные и продуктовые ограничения;
* приоритеты;
* scope;
* что считать хорошим результатом.

Codex отвечает за:

* выбор подходящей технической реализации;
* структуру кода;
* библиотеки из уже разрешённых;
* внутреннюю архитектуру;
* инструменты разработки;
* тестирование;
* реализацию;
* техническое качество проекта.

Пользователь не является разработчиком игр или frontend-разработчиком и не обязан принимать низкоуровневые технические решения.

---

## Самостоятельность в технических решениях

Если техническое решение:

* не меняет существенно пользовательский опыт;
* не создаёт значительных эксплуатационных ограничений;
* не увеличивает существенно стоимость или сложность проекта;
* легко изменить позднее;

Codex должен принять такое решение самостоятельно.

Не спрашивай пользователя без необходимости:

* какой framework использовать;
* какую rendering library использовать;
* как организовать state management;
* какой test runner выбрать;
* как структурировать внутренние модули;
* какой паттерн проектирования применить;
* какие внутренние API создать.

Выбирай разумный вариант сам и при необходимости кратко объясняй решение.

Выноси решение на пользователя только тогда, когда варианты имеют существенно разные последствия для:

* игрового опыта;
* возможностей продукта;
* производительности;
* поддерживаемых устройств;
* сроков;
* стоимости;
* безопасности;
* будущего развития проекта.

Если требуется решение пользователя, не задавай абстрактный технический вопрос.

Вместо этого:

1. объясни проблему человеческим языком;
2. предложи рекомендуемый вариант;
3. при необходимости покажи 1–2 разумные альтернативы;
4. объясни реальные различия между ними.

---

## Основной принцип разработки

Предпочитай рабочее, простое и проверяемое решение преждевременной универсальности.

Не строй архитектуру для гипотетического будущего.

Начинай с минимального решения, достаточного для текущей задачи, и усложняй его только при появлении реальной необходимости.

Не переписывай работающие части проекта без причины, относящейся к текущей задаче.

---

## Перед началом работы

Перед существенным изменением:

1. Изучи текущее состояние репозитория.
2. Прочитай относящиеся к задаче документы.
3. Проверь существующую реализацию.
4. Кратко сформулируй план.
5. Реализуй только необходимый объём.

Если существует небольшая неоднозначность, которую можно разрешить безопасным и легко обратимым предположением, прими решение самостоятельно и сообщи о нём.

Не останавливай работу ради вопроса, если разумное решение очевидно и не имеет существенных последствий.

---

## Требования к игре

Когда существует `docs/GAME_SPEC.md`, считай его основным долговременным источником продуктовых требований.

Более свежая явная инструкция пользователя имеет приоритет над документом.

Если код и `GAME_SPEC.md` расходятся, не изменяй молча одно под другое.

Укажи расхождение и определи, что должно считаться актуальным поведением.

---

## Архитектура

Не требуется заранее создавать отдельный архитектурный документ.

Codex может самостоятельно принимать внутренние архитектурные решения.

Создавать `docs/ARCHITECTURE.md` имеет смысл только если архитектура становится достаточно сложной и документ реально помогает:

* понимать систему;
* сохранять значимые решения между сессиями;
* объяснять границы компонентов;
* фиксировать важные компромиссы.

Не спрашивай пользователя подтверждать обычные внутренние архитектурные решения.

Если архитектурное решение создаёт существенные долгосрочные последствия, объясни их пользователю до реализации.

---

## Работа с зависимостями

Управление внешними зависимостями выполняет только пользователь.

Codex не должен самостоятельно скачивать, устанавливать, обновлять или удалять зависимости.

Запрещено самостоятельно выполнять:

* `npm install`;
* `npm ci`;
* `npm update`;
* `npm uninstall`;
* `npx`, если требуется скачивание отсутствующего пакета;
* `curl` или `wget` для получения внешнего кода;
* `git clone`;
* `git fetch`;
* `git pull`;
* другие действия, предназначенные для загрузки внешнего кода или пакетов.

Не изменяй без явного разрешения пользователя:

* `dependencies`;
* `devDependencies`;
* `optionalDependencies`;
* `peerDependencies`;
* версии зависимостей;
* `package-lock.json` вручную.

Разрешено:

* использовать уже установленные зависимости;
* изучать их локальные типы, документацию и исходный код;
* импортировать их в проект;
* запускать уже существующие npm scripts.

Если нужна новая зависимость:

1. назови пакет;
2. объясни, какую проблему он решает;
3. скажи, насколько разумно реализовать это без него;
4. укажи, runtime это dependency или development dependency;
5. предложи рекомендуемый вариант;
6. остановись и дождись установки пользователем.

Не выбирай дополнительную библиотеку только ради экономии нескольких строк простого собственного кода.

## Изменение технологической основы

Codex может самостоятельно выбирать конкретные технологии реализации, если они ещё не зафиксированы и выбор не имеет существенных продуктовых последствий.

Не заставляй пользователя выбирать технологии только потому, что существует несколько вариантов.

При выборе ориентируйся прежде всего на:

* требования `GAME_SPEC.md`;
* скорость получения работающей версии;
* качество игрового опыта;
* поддержку целевых устройств;
* производительность;
* простоту разработки и отладки;
* размер и сложность кодовой базы;
* зрелость технологии;
* минимальное количество зависимостей.

Новый крупный framework, game engine, runtime, backend, база данных или инфраструктурный сервис требует более сильного обоснования, чем небольшое внутреннее техническое решение.

Если выбор серьёзно влияет на дальнейшее развитие проекта, сначала кратко изложи рекомендацию и компромиссы.

---

## Разработка игры

При реализации игровой функциональности начинай с опыта игрока, а не с внутренней архитектуры.

Для существенной механики сначала определи:

* что делает игрок;
* что он видит или слышит в ответ;
* какое состояние игры меняется;
* что делает действие понятным и приятным;
* как проверить, что механика работает правильно.

Техническая реализация должна обслуживать игровой опыт.

Не заменяй хороший игровой опыт сложной архитектурой.

---

## Итеративная разработка

Предпочитай небольшие законченные vertical slices.

После появления новой механики должно быть возможно как можно раньше её запустить и оценить.

Не реализуй большой набор взаимозависимых систем до того, как основная механика проверена в игре.

Если задача слишком большая, самостоятельно разбей её на последовательные работающие этапы.

Каждый этап по возможности должен оставлять проект запускаемым.

---

## Проверяемость игры

По мере развития проекта делай игровое состояние удобным для диагностики.

Когда это действительно полезно, используй:

* воспроизводимые стартовые состояния;
* небольшие тестовые сцены;
* детерминированные сценарии;
* диагностическое представление состояния игры;
* performance counters;
* автоматизированные пользовательские сценарии.

Не создавай тяжёлую тестовую инфраструктуру заранее.

Добавляй инструменты проверки тогда, когда они заметно ускоряют разработку или предотвращают реальные ошибки.

---

## Ручное тестирование

Для таких вещей, как:

* управление;
* камера;
* движение;
* анимации;
* визуальная читаемость;
* feedback действий;
* ощущение боя;
* responsiveness;

автоматические тесты не являются достаточной проверкой.

После значимых изменений такого типа сообщи пользователю, что именно стоит проверить вручную.

Не утверждай, что механика «приятная» или «хорошо ощущается», если это не было проверено человеком на реальном устройстве.

---

## Автоматические проверки

Объём проверки должен соответствовать риску изменения.

Используй существующие средства проверки проекта.

Когда они доступны и относятся к изменению, запускай:

* typecheck;
* unit tests;
* lint;
* production build;
* integration/browser tests.

Не создавай тесты ради формального покрытия.

Игровую логику, которую удобно проверять детерминированно, желательно отделять так, чтобы её можно было тестировать без полноценного рендеринга игры.

Если проверка падает из-за твоего изменения, исправь проблему до завершения задачи.

Если проверку невозможно выполнить, явно сообщи об этом.

---

## Производительность

Не оптимизируй без измерений, если только проблема не очевидна.

Особенно внимательно относись к коду, выполняющемуся каждый кадр.

Избегай без необходимости:

* большого количества аллокаций в hot path;
* обработки невидимых объектов;
* полного пересчёта больших структур каждый кадр;
* лишнего rendering work;
* дорогостоящих синхронных операций в основном игровом цикле.

Если задача посвящена производительности:

1. выбери измеримый показатель;
2. измерь исходное состояние;
3. найди источник проблемы;
4. внеси изменение;
5. повтори измерение;
6. сравни результаты.

Полезные показатели могут включать:

* frame time;
* FPS;
* количество активных объектов;
* draw calls;
* объём памяти;
* количество аллокаций;
* время загрузки;
* размер bundle;
* время выполнения конкретной операции.

Не выдавай результаты искусственного benchmark за производительность реального телефона.

---

## Отладка

При проблеме используй цикл:

1. воспроизведи проблему;
2. собери наблюдаемые факты;
3. найди соответствующий код;
4. сформулируй вероятную причину;
5. внеси минимальное исправление;
6. повтори исходный сценарий.

Не вноси случайный набор изменений в надежде устранить симптом.

---

## Git

Codex может самостоятельно использовать Git и создавать commits.

Перед commit:

1. выполни `git status`;
2. просмотри diff;
3. убедись, что изменения относятся к текущей задаче;
4. выполни необходимые проверки.

Создавай commit после логически цельного изменения.

Предпочитай небольшие содержательные commits.

Сообщение commit должно кратко описывать результат изменения.

Без явной команды пользователя запрещено:

* переписывать Git history;
* делать destructive reset чужих изменений;
* force push;
* удалять `.git`;
* удалять или перезаписывать несвязанные пользовательские изменения.

Не включай в commit:

* секреты;
* временные файлы;
* случайные логи;
* debugging artifacts;
* ненужные generated files.

---

## Документация

Репозиторий является долговременной памятью проекта.

Не рассчитывай на информацию, которая существовала только в предыдущей сессии Codex.

Документируй только знания, которые действительно полезно сохранить между сессиями.

Не создавай новый документ, если несколько строк в существующем документе лучше решают задачу.

Поддерживай документацию в соответствии с актуальным состоянием проекта.

---

## Большие задачи

Для небольшой задачи достаточно короткого плана в текущей сессии.

Для большой многоэтапной задачи Codex может создать план в `docs/plans/`, если это действительно помогает сохранять состояние работы.

Такой план должен содержать только полезную информацию:

* цель;
* scope;
* этапы;
* критерии готовности;
* важные решения;
* риски;
* текущий прогресс.

Не создавай планы ради формальности.

---

## Завершение задачи

Перед завершением:

1. убедись, что запрошенное поведение реализовано;
2. проверь релевантные сценарии;
3. запусти необходимые автоматические проверки;
4. просмотри итоговый diff;
5. убери случайные временные изменения;
6. при логически завершённой работе создай Git commit.

В итоговом сообщении кратко укажи:

* что сделано;
* как это проверено;
* что пользователь должен проверить вручную;
* известные ограничения или открытые вопросы.

Не перегружай итоговое сообщение подробностями реализации, если пользователь их не просил.
