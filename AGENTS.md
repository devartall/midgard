# AGENTS.md

## Назначение

Этот файл содержит постоянные правила работы Codex с репозиторием.

Не превращай `AGENTS.md` в полное описание проекта. Подробные требования, архитектурные решения, планы и технические спецификации должны храниться в `docs/`.

Перед существенной работой изучай относящиеся к задаче документы из `docs/`, если они существуют.

Предполагаемая структура документации:

* `docs/GAME_SPEC.md` — продуктовые требования и игровая механика;
* `docs/ARCHITECTURE.md` — архитектура и ключевые технические решения;
* `docs/TECH_STACK.md` — утверждённые технологии и зависимости;
* `docs/PLANS.md` или `docs/plans/` — планы значительных изменений.

Если какого-либо документа ещё нет, не придумывай его содержимое.

## Основной принцип

Человек задаёт цели, ограничения и принимает продуктовые решения.

Codex выполняет инженерную работу внутри этих границ.

Предпочитай рабочее и проверяемое решение преждевременной универсальности и архитектуре «на будущее».

## Перед началом работы

Перед существенным изменением:

1. Изучи текущее состояние репозитория.
2. Прочитай относящиеся к задаче документы.
3. Проверь существующую реализацию прежде, чем предлагать новую.
4. Кратко сформулируй план.
5. Выполняй только объём, необходимый для текущей задачи.

Если неоднозначность действительно может существенно изменить результат, явно обозначь её.

Если можно сделать безопасное и легко обратимое предположение, сделай его и сообщи об этом.

## Работа с зависимостями

Управление внешними зависимостями выполняет только пользователь.

Codex не должен самостоятельно скачивать, устанавливать, обновлять или удалять зависимости.

Запрещено самостоятельно выполнять:

* `npm install`;
* `npm ci`;
* `npm update`;
* `npm uninstall`;
* `npx`, если команда требует скачивания отсутствующего пакета;
* `curl` или `wget` для получения внешнего кода;
* `git clone`;
* `git fetch`;
* `git pull`;
* другие действия, предназначенные для загрузки внешнего кода или пакетов.

Не изменяй без явного разрешения пользователя:

* `dependencies`;
* `devDependencies`;
* `optionalDependencies`;
* `peerDependencies`;
* версии зависимостей;
* `package-lock.json` вручную.

Разрешено:

* использовать уже установленные зависимости;
* читать их локальную документацию, типы и исходный код;
* импортировать их в код проекта;
* использовать существующие npm scripts.

Если полезна новая зависимость:

1. назови пакет;
2. объясни, какую проблему он решает;
3. объясни, насколько разумно реализовать это без новой зависимости;
4. укажи, является ли зависимость runtime или development dependency;
5. остановись и дождись решения пользователя.

Считай произвольный доступ к интернету недоступным.

## Изменение технического стека

Не добавляй самостоятельно:

* новый framework;
* новый game engine;
* новый runtime;
* новый package manager;
* новую систему сборки;
* backend;
* базу данных;
* инфраструктурный сервис.

Если такое изменение кажется оправданным, сначала опиши:

1. проблему;
2. предлагаемое решение;
3. преимущества;
4. недостатки;
5. альтернативу без изменения стека.

После этого дождись решения пользователя.

## Качество реализации

Предпочитай:

* простой и читаемый код;
* небольшие сфокусированные модули;
* понятные имена;
* явные зависимости;
* минимальное скрытое состояние;
* минимально необходимый уровень абстракции;
* решения, которые легко проверять и отлаживать.

Не создавай абстракции только ради возможных будущих требований.

Не переписывай работающий код без причины, относящейся к текущей задаче.

Не изменяй несвязанные части проекта ради косметического улучшения.

## Разработка игры

При реализации игровой функциональности начинай с поведения, которое должен увидеть и почувствовать игрок, а не с внутренней архитектуры.

Для каждой существенной механики сначала пойми:

* что игрок делает;
* что он должен увидеть или услышать;
* какое состояние игры меняется;
* как определить, что механика работает правильно.

Техническая реализация должна обслуживать этот опыт.

Для ощущения управления, движения, камеры, анимаций и визуальных эффектов автоматические тесты не заменяют ручное тестирование.

## Проверяемость игры

По мере развития проекта делай игровое состояние понятным и доступным для диагностики.

Когда это оправдано, предпочитай:

* воспроизводимые стартовые состояния;
* небольшие тестовые сцены;
* детерминированные сценарии;
* диагностический интерфейс состояния игры;
* счётчики производительности;
* возможность быстро воспроизвести конкретную проблему.

Не создавай сложную тестовую инфраструктуру заранее. Добавляй её тогда, когда она позволяет надёжнее и быстрее проверять реальные игровые функции.

Если браузерные тесты или другие средства автоматизации уже доступны в утверждённом стеке, используй их для важных пользовательских сценариев.

## Тестирование

Объём проверки должен соответствовать риску изменения.

Не создавай тесты ради тестов для небольших, очевидных и легко обратимых изменений.

Для игровой логики, которая может быть проверена детерминированно, предпочитай автоматическую проверку.

После существенного изменения выполни доступные проверки, относящиеся к нему:

* typecheck;
* unit tests;
* lint;
* production build;
* релевантные integration/browser tests.

Не повторяй весь набор дорогих проверок без причины, если необходимые проверки уже прошли и код после этого не менялся.

Если проверка падает из-за твоего изменения, исправь проблему до завершения задачи.

Если проверка не может быть выполнена, явно сообщи об этом.

## Производительность игры

Не оптимизируй вслепую.

Если проблема связана с производительностью:

1. определи измеримый показатель;
2. зафиксируй исходное состояние, если это возможно;
3. найди источник нагрузки;
4. внеси изменение;
5. повтори то же измерение;
6. сравни результаты.

Используй подходящие метрики, например:

* время кадра;
* FPS;
* количество отображаемых объектов;
* draw calls;
* объём памяти;
* число создаваемых объектов;
* объём загружаемых или генерируемых данных;
* время выполнения тяжёлой операции.

Не выдавай измерения из искусственной среды за реальную производительность устройства.

Финальная оценка плавности и ощущения игры должна включать ручное тестирование.

## Отладка

При ошибке предпочитай цикл:

1. воспроизвести проблему;
2. собрать наблюдаемые факты;
3. определить соответствующий код;
4. сформулировать причину;
5. внести минимально необходимое исправление;
6. повторить исходный сценарий проверки.

Не исправляй симптомы случайными изменениями, если можно определить причину.

## Git

Codex может самостоятельно использовать Git и создавать commits.

Перед commit:

1. проверь `git status`;
2. просмотри `git diff`;
3. убедись, что изменения относятся к текущей задаче;
4. выполни необходимые проверки.

Делай commit после завершения логически цельного изменения.

Предпочитай небольшие содержательные commits с понятными сообщениями.

Без явной команды пользователя запрещено:

* переписывать историю;
* выполнять destructive reset чужих изменений;
* удалять `.git`;
* делать force push;
* удалять или перезаписывать несвязанные пользовательские изменения.

Не включай в commit временные файлы, логи, артефакты отладки или секреты.

## Документация и архитектурные решения

Репозиторий является источником долговременного контекста проекта.

Не рассчитывай на информацию, существующую только в прошлой сессии Codex.

Если принято существенное долговременное решение, предложи зафиксировать его в соответствующем документе `docs/`.

Если код расходится с существующей спецификацией, не исправляй молча спецификацию или код.

Сообщи о расхождении и определи, что должно считаться источником истины.

## Планы больших изменений

Для небольшой задачи достаточно краткого плана в текущей сессии.

Для большой, многоэтапной или архитектурной работы предложи создать или обновить отдельный план в `docs/plans/`.

План должен содержать:

* цель;
* ограничения;
* этапы;
* критерии готовности;
* ключевые решения;
* выявленные риски.

По мере выполнения поддерживай такой план актуальным, если он используется как рабочий документ.

## Завершение задачи

Перед тем как считать задачу выполненной:

1. убедись, что запрошенное поведение реализовано;
2. проверь относящиеся к изменению сценарии;
3. запусти необходимые автоматические проверки;
4. просмотри итоговый diff;
5. убери случайные и временные изменения;
6. при логически завершённой работе создай Git commit.

В итоговом сообщении кратко укажи:

* что изменено;
* как это проверено;
* какие известные ограничения остались;
* требуется ли действие пользователя.
